# CCA 试点需求 · 仓库初始化、上下文合流与 TT 提醒

2026 年 11 月 23 日 · 供 Codex 开发与验收

## 1. 首次进入仓库，先确认它承载什么

1. 接手时先读取该仓已确认的范围。新仓或范围未明确时，先问仓库负责人：「这个仓最主要服务哪个项目，接下来希望它承载哪些方向？」根据回答，用一轮一问补齐首批议题、包含与排除的边界、跨项目条目应该找谁。遇到多项目例会，可以据材料提出候选，但由负责人确认主项目。
2. 复述范围让负责人确认，保存项目、主旨、首批议题、边界、维护角色和确认依据。以后接手直接复用。范围变更也经负责人确认并留痕。确认前只暂存在受限入口，暂停正式归档和自动转交。
3. 收到材料按议题逐条判断。属于本仓或直接影响本仓的内容，按[卡片模板](../templates/context-card.md)制卡，记录事实或建议、适用范围、状态、证据位置，以及明确的负责人和下一步。属于其他项目的提炼必要内容后，按授权转交。归属不清时先留待确认。
4. 例如周五例会同时讲了 AI Native 试点、内容审核方案和独立运营事务。确认 AI Native 是本仓主项目后，保存试点范围与拍板原话。内容审核和运营各走对应项目。若内容审核给试点提供一个依赖，本仓只留这条依赖。

## 2. 要跑通的场景

以 AI Native 舱为首个试点。周五例会覆盖三个项目，CCA 能听清本项目谁拍了什么板，把决定交给执行人，把其他项目的条目交给对应负责人。漏掉的小范围讨论可以用语音或 Codex 成果补进来。真正需要拍板时，负责人收到一条可以处理的提醒。

TT 指 TeamTalk，是团队的即时通讯入口。接入能力以授权环境实测结果为准。

## 3. 听清会议结论

- 结合前后句、否定、条件和范围解读纪要。按议题提取建议、决定、待确认项和执行动作。人工纪要可辅助核对，矛盾时保留两处证据。
- 决定记录谁说的、拍板原话或时间点、允许做到哪一步和适用项目。执行动作记录接手人和期限。缺失的信息留空，注明待确认。会议室设备名不能当作个人身份。
- 例：「我建议继续」是建议。「可以继续，先做低保真，周二我看」只批准低保真和周二 review。发言人、权限和范围都可核验，且符合该事项既定审批要求时，记录会议批准依据并交给执行人，无需再发审批。
- 听不清谁说的，或已有决定与新说法冲突，只问一个能解决问题的问题。例：「三个流程改成一个，还是先做一个、之后再扩？」影响正式决定的确认记录由对应授权角色完成。

## 4. 补录、项目分发和写入

1. 项目成员可以从 CCA 语音入口补一句，也可以从 Codex 提交阶段成果、变更或产物链接。让提交人看到已进入哪一处、是否需要确认。记录提交时间与可得的实际发生时间，以来源、语义和适用范围核对已有卡。隔天补录也能正常进入流程。
2. 同一个事实补证据，沿用卡片 ID。紧贴主线且无冲突的补充，直接挂在主线议题下，按事实或方案保存，保留来源。既有已批准决定可挂补充证据。符合 L1 且可核验的事实、或已有完整批准依据的决定，才进入正式生效的 Main。Codex 做出的原型按方案收录，交付完成本身不代表批准。
3. 另起方向先进待定，动作是请对应议题负责人看是否值得探索。已明确是验证某个假设的方案可进 Exploration，并标注「待验证」。改动已有决定先进入 Pending，列出旧内容、新内容、影响和确认人。确认时校验授权和当前版本，通过后归档旧版并互链。逾期保持待审。
4. 多项目会议逐项归属。AI Native 舱只收与自身工作有关的内容。第二、第三项目各生成短卡，包含最小必要事实、决定或建议、负责人及下一步。仅转交有权限的对应负责人。归属或权限不清，放在受限待转交队列。没有行动价值的内容过滤，整份纪要留在授权源。
5. 项目成员有提交权。CCA 服务只写被授权的目标和分区。既有规则继续按 L1 低风险事实、L2 议题负责人确认、L3 正式规则或关键决策的授权角色及必要会签生效。仓库负责人也按所涉议题授权走。对外公开另行审批，原文、身份映射、内部链接及未经批准的摘要保留在受限环境。团队可见和公开发布是两种权限。当前公开上下文仓只接收获准公开的提炼件。

## 5. TT 拉取、交接和提醒

### 拉取

- 只接入已授权的试点群、会议来源和成员提交入口。优先用平台事件订阅接收新增，有授权的增量查询则用于补漏和恢复。只有查询时按来源游标定期拉取，可初设每 15 分钟。两种能力均缺失时走授权导入，并显示覆盖缺口。缺少有效的上次归档点时，记录实际覆盖的起止范围与缺口，再小范围回补。
- 以来源、事件 ID 和版本去重。提交入库成功后再推进该来源游标。同一页失败可重跑。历史补拉先入待核对列表，生成一次汇总。仍然待拍板且满足紧急条件的条目才走即时提醒。
- Codex 开始或恢复任务时，主动拉取有权查看、适用于当前任务的最新 Main。方案和待定项可单独展示并注明状态。提醒已发与 Codex 已加载上下文分别记录。

### 提醒

- 群里默认静默。用户主动 @ 或发起提交时，可以回一个结果或一个澄清问题。一般待办进对应责任人的清单，周二、周四上午汇总。负责人的具体收件时间可配置，无新增和到期项时跳过发送。
- 给仓库负责人的汇总优先列已确认结论和能直接开工的下一步。探索或待确认事项同时满足价值高、提交人标急，才请其介入。确实卡住执行、等不到下一次汇总，且其有权拍板时，立即私聊。其他事项找对应议题负责人。
- 例：「今天五点锁范围。请确认试点是否只做一个流程。你同意后，研发开始做。」附可访问的依据，并提供同意、退回、稍后处理。支持经验证的审批回传时用卡片，否则私聊短消息带到受限审批入口。计划中的最后一次提醒只发给仍待审且临近截止的请求。处理完成、撤回或批准版本被替换后，取消旧提醒。稍后处理应记录下次时间，逾期继续留在待办。
- 相同请求、接收人和提醒阶段只发一次。发送超时先查回执再补发。发送成功、读到消息和拍板分别记录。审批时校验本人、授权和对应版本。重复点击只处理一次。私聊失败留在受限待办，可用已授权入口查看，群里保持静默。

## 6. Codex 首个开发切片与验收

复用现有上下文模型、分区和版本逻辑。先以三个项目的合成例会、一条语音补录、一份 Codex 成果跑一遍，再用一个授权测试群和测试账号接入真实平台。

1. 新仓收到三项目会议时先问主项目和核心议题，范围确认前正式归档为空。确认后生成本仓卡，第二次接手沿用范围。
2. 同一场会中，「建议做」留在建议，「负责人同意先做低保真」按范围入账并交给执行人。没有重复审批。身份不明时只生成一个确认问题。
3. 周五补周三的支持材料，挂到原议题并保留来源。范围从三个变成一个时，原决定保持生效，产生一条待审变更。新 Codex 原型保持方案状态。
4. 其余两项目各只交接一次。接收人无权查看时，无内容泄漏。AI Native 默认检索只返回本舱适用上下文。
5. 日常事项进汇总，真的卡工且符合条件的私聊。重复拉取、中断重跑、重复点击均不产生第二张卡、第二次相同提醒或第二次审批。已处理的卡片停止提醒。
6. 平台接入分别验收群事件或历史增量、可识别发言者的来源引用、指定用户私聊、卡片回传及其权限。现有 TeamTalk 消息服务和机器人互动资料可以支持设计发送侧。历史查询的覆盖范围、事件订阅、审批回传和服务账号权限需用沙箱核实。仅能发送时也能走导入和受限审批页。模拟通过和真实接入通过分别报告。
